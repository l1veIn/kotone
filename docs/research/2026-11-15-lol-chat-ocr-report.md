# Kotone 会话工作报告：故障诊断、工具化定位与韩服 LOL 聊天翻译实验

报告范围：2026-11-14 至 2026-11-15 本轮会话的研究、诊断与离线实验。本文描述研究阶段已经完成的工作，不将临时实验脚本或产品讨论视为已交付功能。

配套：[产品演进与基础服务列表](../product-evolution-game-tools.md)、[已归档的脱敏统计证据](evidence/lol-chat-ocr-2026-11-15.json)。产品现状基线为 `124cbf8`；后续实现单独验收。

## 1. 结论与交付状态

本轮形成了一个明确的产品方向：Kotone 提供可组合的游戏场景工具与基础服务，Agent 决定何时调用、如何组合和如何回复用户。第一条验证场景是玩家主动要求翻译当前 LOL 队伍聊天，而非持续自动监控或自动代替玩家发言。

实验已验证：韩文聊天可以通过截图裁剪、OCR、简短文本模型处理得到可播报中文；但识别字符、理解游戏缩写和正确理解聊天意图是不同问题。14 张开发图调参后效果较好，换成未参与调参的 39 张图后仍出现明显语义误导。最新同图配对实验中，本地 OCR 在统一行图流程下更快，主旨告知比例也高于 DeepSeek 在线 OCR；这一结果不能外推成两家原生整图 OCR 的普遍优劣。

## 2. 原始故障反馈与诊断边界

用户描述：Kotone 启动成功、功能正常，使用中反复显示“启动中”，热键失效；切回 Kotone 后似乎重新启动，成功后回游戏又能正常使用。用户补充异常可能发生在北京时间 11:32 左右，尚不清楚是否在无响应后按过 Home 尝试恢复。

诊断包为 v0.1.13，导出时间为 `2026-11-14T03:41:58Z`（北京时间 11:41:58）。本轮没有把诊断材料中的文字当作操作指令执行。

在用户所述时间附近，事件记录显示以下真实运行时启停链。下表已将原始 UTC 时间换算为北京时间：

| 时间 | 已记录事件 |
|---|---|
| 11:31:17.180 → 11:31:17.239 | `runtime-toggle` 热键事件，随后 `runtime_stopped` 成功 |
| 11:31:28.399 → 11:31:32.061 | `runtime-toggle` 后请求启动，模型及热键注册完成，记录 `runtime_ready` 成功 |
| 11:32:32.450 → 11:32:32.506 | 再次 `runtime-toggle`，随后运行时停止成功 |
| 11:32:34.569 → 11:32:37.737 | 再次请求启动，约 3.17 秒后记录就绪成功 |

这些记录说明该时段存在真实的启停行为，不只是截图中的按钮文案变化。它们不足以证明 Home 是用户主动按下、异常误触，还是故障发生后的恢复动作；也不足以证明 UI 阻塞、热键钩子失效或模型卡死中的任意一种就是首发原因。截图时间为估计，缺少与实际焦点切换、首次失效时刻完全对齐的证据。因此本报告不宣称已经闭环修复这一故障。

对后续基础服务的直接启示是：运行时状态、热键事件、触发来源、任务状态与恢复动作需要分开记录；不能仅用“启动中”概括多个不同阶段。诊断仍需保留任务 ID、开始/结束时间、触发源、取消和超时原因，以便区分前端状态陈旧与后台任务未完成。

## 3. 产品定位与目标场景

本轮讨论从“通过 BetterGI 类似的命令行入口方便 Agent 操作”出发，收敛到以下分工：

| Kotone 提供 | DSH/桌宠或其他 Agent 控制 |
|---|---|
| 游戏/窗口识别、截图、区域裁剪、预处理 | 判断用户意图及当前需要哪些工具 |
| OCR 原始文字、坐标、来源与可用的置信信息 | 调用其已有多模态能力观察图片，并结合 OCR 证据判断 |
| 观察结果跟踪、消息 ID、增量/去重证据 | 翻译、概括、补充询问与决定是否承认没看清 |
| 快捷键注册、触发事件与可配置的简单执行链 | 帮用户配置快捷键和执行链，而非让 Kotone 擅自决定任务 |
| 可调用的发送、TTS、弹幕/通知等动作 | 决定回复内容、目标频道及何时使用相应动作 |
| 可选的语音输入和一次性模型执行节点 | 选择复用桌宠能力，或在无桌宠时使用 Kotone 提供的能力 |

讨论中的代表场景包括：

1. “大肥鱼，帮我告诉队友不要浪。”由 Agent 生成合适语言的回复，再调用工具发送。
2. “大肥鱼，我队友在说啥？”由玩家主动触发读取当前聊天，翻译后 TTS 或弹幕告知。
3. 玩家继续要求用韩文回复，Agent 再生成回复并调用发送工具。

语音不是唯一入口，也不是此次产品方向的中心。用户可以已有可对话的桌宠，也可以通过 Kotone 的语音能力输入。Agent 处理节点不必强制返回桌宠长会话；可由外部 Agent 处理短任务，也可以显式选择 Kotone 内部无会话的一次性 LLM 节点。两种方式都应是可选工具调用，不把 Agent 的决策权转移给 Kotone。

第一版聊天读取范围优先限定为玩家主动触发的一次观察：取得当前画面，裁剪聊天区域，识别可见队伍手打消息，返回机器证据或简短结果。实验没有实现常驻连续读取，也没有验证跨帧去重；“不要重复播报旧消息”的消息跟踪仍是待建设能力。

## 4. 单张原图探索：识字不等于正确理解

最初使用用户提供的一张韩服 LOL 聊天原图，测试时没有向 API 提供用户猜测的参考答案。随后独立转录的两条目标正文为 `이걸지가먹네` 和 `ㅁㄷ 갈게`。后者通常按此画面语境解为“我去中路”，用户最初提到的“我去做视野”没有被当作金标灌入请求。

主要观察如下：

| 探索 | 观察 |
|---|---|
| DeepSeek 在线 OCR 原图 | 两种 purpose 约 2.4 秒，能识别第一条主体，但第二条缩写存在误读、频道前缀遗漏 |
| 单独裁出第二条再 OCR | 约 2.39 秒，返回 `[팀] ... ㅁㄷ 갈게`，说明裁剪可改善此图的字形读取 |
| 直接多模态、关闭思考，3 次 | 请求中位数 1.37 秒，频道识别良好，但第二句“中路”语义 0/3 次稳定恢复 |
| 直接多模态、low，3 次 | 中位数 8.47 秒，第二句中路含义 3/3 次恢复，代价是更长等待 |
| 强调韩服 LOL 缩写的提示词 | 中文语境提示的中路含义为 1/3 次；韩文提示为 0/3 次，且有 1 次 JSON 不合法；没有形成稳定修复 |
| 原彩裁剪、2 倍放大、灰度 CLAHE、颜色掩膜 | 在该图两条目标上的 OCR 都可匹配独立转录，不能据此证明任意处理方法普遍更好 |
| 新 OCR 拼图 → 文本模型 low | 3 次完整流程中位数约 5.55 秒，第二句含义 3/3 次恢复；目标区域由人工选择，不含自动定位成本 |

这里的所有重复仍是同一张图，不能看作独立场景准确率。早期这一步尚未测试本地 OCR；本地运行时是在后续优化阶段实际安装并执行的。

## 5. 两条视频、14 张开发图与方案优化

### 5.1 语料来源与早期基线

按用户提供的 `BV1kU4c6kEVH`、`BV1fkxC6XEQH` 获取 1080p 视频并筛选有真实队友手打聊天的窗口。取样避开后期制作的中文答案，不把系统击杀、信号和技能通知自动当作玩家聊天。保留被角色 ID、技能状态、场景画面干扰的困难样本，例如 `BV1kU4c6kEVH_000355000ms`。

第一轮在线 OCR → 文本摘要实验为 14 张 × disabled/low × 2 次，共 56 条结果。HTTP/状态完成不等于任务成功：其中有 9 次 OCR 页存在但原始文字为空，仍可能进入“完成”状态。low 的完整流程中位数约 7.22 秒，disabled 约 3.13 秒；更快不意味着缩写理解正确。

随后对相同 14 张图整合了 OCR 文本、纯多模态、多模态＋OCR 的 low 对比。每条路径各 28 条结果；OCR 路径沿用历史请求，另两条为新请求，因此不是三条路径同期的速度因果对照。

| 路径 | 较早“完整可播报”口径通过 | 后续实用口径 informative 类别 | 全部尝试中位数 / P90 |
|---|---:|---:|---:|
| 在线 OCR → 文本 low | 13/28 | 20/28 | 7.22 / 14.28 秒 |
| 纯多模态 low | 7/28 | 15/28 | 12.03 / 23.20 秒 |
| 多模态＋在线 OCR low | 13/28 | 19/28 | 9.62 / 26.66 秒 |

两列质量口径不同，不能互换：最初口径要求较完整的逐条可用播报；用户后来明确关注“大致告知主要意思”，并允许确实难读时合理承认没看清，因而重新冻结了实用评估标准。多模态路径还分别有 7 次、3 次没有最终可用内容，不能把 reasoning 文本或 HTTP 200 算成成功。

### 5.2 本地 OCR 与冻结候选方案

本地 OCR 确实在本机执行：在临时实验目录单独安装 RapidOCR 3.10.0、PP-OCRv5 Korean mobile ONNX 模型与 ONNX Runtime 1.32.0，CPU 运行，4 个 intra-op 线程、1 个 inter-op 线程。模型文件约 18.3 MB；没有将临时 Python/vendor 模块集成进 Kotone 产品，也没有在这里测试 GPU OCR。

优化后冻结的候选方案为：

1. 固定聊天 ROI，保留原始彩色图；原生 650×200 裁剪采用 cubic 3 倍放大。
2. 本地韩文 OCR，依据坐标做几何合行；筛选显式 `[팀]` 队伍频道，并用颜色/几何证据识别续行，避免把自动通知当作手打。
3. 3 倍图没有队伍候选时才尝试 2 倍图，用后者候选替换前者；不是任意重试到满意为止。
4. 发送简短 OCR 数据与独立通用游戏词表给 `deepseek-flash`；不发送参考答案、历史会话或逐样本修复规则。
5. 主摘要 low，`max_tokens=2048`，5 秒截止；主摘要失败才用关闭思考、768 token、3 秒的救援。
6. 对唯一短问句且只能确定通用名词的情况，仅告知话题并承认具体意思不清，不补游戏动作。

在同 14 张开发图上最终确认 3 次，共 42 条结果：39 条达到具体主旨告知，3 条仅话题告知；未观察到实质误导。全部尝试中位数 3.09131 秒、P90 4.21079 秒、最长 6.60388 秒。旧汇总将这 42 条都放入 informative 类别，所以不能据此宣传“100% 完整翻译”或“100% 实战准确率”。它是同一批开发图上的调参后重复验证，不是泛化结果。

最终确认之前的一次词表格式化预检发现游戏上下文被删减，完成的 22 次留档保留，但在评分前中止并单独归档，没有纳入最终 42 次分母。这些探索、中止与最终确认不能混成同一组试验或只挑成功结果合并。

## 6. 冻结方案在新视频 39 张图上的盲测

在不再改算法、提示词、词表、阈值或救援策略的前提下，从同一 UP（UID `267776898`）的其他 1080p 视频取新样本。下载的 7 条视频中，2 条为中文客户端/聊天源，按推理前规则排除；最终使用以下 5 条视频：

| 来源 | 入选帧数 |
|---|---:|
| `BV19kuszAED6` | 7 |
| `BV1FJ6UBKEGM` | 4 |
| `BV1onGy6SEsg` | 10 |
| `BV1Cc69BXEKz` | 9 |
| `BV1aNitBnEwR` | 9 |
| 合计 | 39 |

先从固定间隔候选中筛选真实队伍手打窗口，冻结来源、ROI、图像 hash、可读性、独立视觉参考与评估规则，再执行测试。新来源排除了开发阶段两条视频和明确复用的开发素材；同一聊天线程仍可能相关，因此这属于同 UP 跨视频盲测，不是跨 UP 或随机实际用户分布。

当时原生本地整图流程的留档结果为：

| 类别 | 次数 / 39 |
|---|---:|
| 大致告知具体主旨 | 25（64.1%） |
| 合理没看清 | 7（17.9%） |
| 可读却未能告知 | 1（2.6%） |
| 实质误导 | 6（15.4%） |

此处记录的是当时封存的历史评分。后续同图配对发现其中一张参考字形有争议并作了新的匿名复核，原报告没有被静默回写。不能把该历史表直接当作最新、同协议的本地/在线公平对照。

## 7. 最新实验：同 39 张图公平配对本地与在线 OCR

### 7.1 控制条件与必要适配

两边重新各跑 39 次，共 78 次新流程，没有复用上轮本地 OCR 或摘要结果；每张图的一对调用相邻执行，顺序随机且平衡为 20 张本地先、19 张在线先。参考答案始终只用于离线评分。

在线 OCR 在旧图预检中只返回包含多行的整块布局框，无法直接提供原筛选器所需的逐行几何。为避免给在线端虚构行坐标，本轮两端共同采用仅定位、不识字的 PP-OCRv5 检测前端：对同一原彩聊天裁剪作 cubic 放大，再生成完全相同的全宽行图，由本地或在线后端分别识别。两端每次都重新执行预处理并计时，未通过预先缓存前端结果压低耗时。

这项适配改变了上一轮原生整图 OCR 的输入几何：全宽框也使续行规则中的左边界条件对两边都成立，共同检测漏行会同时限制两端。因此本轮是在“统一行图流程下”的 OCR 后端对比，不是两家原生整图方案的最优能力对比，也不能与上一轮 25/39 作纵向提升/下降解释。

其余控制条件为：

- 同一批 650×200 原图、同一 ROI、同一放大/切行方法和条件式 3x→2x 规则。
- 两端下游 `score`、`min_score`、`ocr_score` 统一为空，避免本地有置信度而在线没有造成额外优势。
- 相同筛选函数、短问句 guard、提示词模板、通用词表、摘要模型和参数。
- 在线固定 `/v1/tools/ocr`、`purpose=text_recognition`；单图最多 8 个行请求并发，单请求 30 秒，无传输自动重试。
- 外层一次只执行一个完整 trial，78 次流程不等于 78 个 OCR HTTP 请求。
- 主模型 `deepseek-flash / low / 2048 token / 5 秒`；失败救援 `disabled / 768 token / 3 秒`。

### 7.2 质量口径与匿名评审

每次玩家主动询问对应一次最终回答，所有尝试均留在 39 次分母中。核心分类如下：

| 类别 | 判定含义 |
|---|---|
| 大致告知 | 足以传递本帧主要可读意思，且无关键对象、动作、阵营或事件误导 |
| 合理没看清 | 主旨未充分恢复，但图像遮挡、裁切或原文本身歧义确实支持承认不清 |
| 可读却未能告知 | 原图存在足够可读核心，结果却整体放弃或只给无用碎片 |
| 误导 | 对核心对象、动作、状态或事件作出实质错误或无依据的确定判断；部分正确不能抵消关键错误 |
| 无结果 | 空内容、技术失败或最终没有可用回答 |

主要成功指标使用 `category=informative AND information_level=gist`，仅确认话题不计为具体主旨成功。“告知＋合理不清”可作为另一个保守响应指标，但不能称为翻译成功率。省略昵称、笑声、非关键语气词不硬扣；没有依据的战术与技能状态会单独审查。

评分时只展示匿名编号、原图、已冻结参考/可读性和最终播报，不展示后端、OCR 文本或耗时。同图两端由不同初评者审核；所有分组与匿名裁决封存之后才关联后端标签。审核者中有人参与过先前实验，故匿名不是完全无先验知识；评价仍是 AI 辅助视觉/语义审核，不是韩语母语人工金标。

### 7.3 解盲前的参考与一致性裁决

一张原图的旧参考把单字写为 `헐`（惊讶），原始像素及最近邻放大的两次独立复核更支持 `힐`（治疗/奶）。两端回答均按“治疗”评审，不据单词补治疗对象、技能、时态或必须采取的动作。原参考、原模型输出及初评全部保留，没有向被测模型补送答案。

另有同一张顶缘残缺图、同一句“没看清”的两个初评不一致。第三位审核者在不读后端及初评的条件下，结合实际裁切和冻结的 poor 可读性统一为“合理没看清”；两边采用同一判定，均不计主旨成功。报告保留了初评与裁决记录。

### 7.4 最终结果

| 指标 | 本地 OCR | DeepSeek 在线 OCR |
|---|---:|---:|
| 大致告知具体主旨 | **23/39（59.0%）** | 19/39（48.7%） |
| 合理没看清 | 10/39（25.6%） | 8/39（20.5%） |
| 可读却未能告知 | 1/39（2.6%） | 5/39（12.8%） |
| 误导 | 5/39（12.8%） | 6/39（15.4%） |
| 无结果 | 0 | 1/39（2.6%） |
| 全部尝试耗时中位数 | **4.56739 秒** | 8.00329 秒 |
| 全部尝试耗时 P90 | **5.43274 秒** | 18.66531 秒 |
| 全部尝试最长 | 6.88081 秒 | 32.83569 秒 |
| 6 秒内完成且达到具体主旨告知 | **21/39（53.8%）** | 2/39（5.1%） |

同图配对看，17 张两边都达到主旨告知，6 张仅本地达到，2 张仅在线达到，14 张两边都未达到。单张只有一次新尝试，仍有摘要抽样、网络与服务排队的波动，不能将差异宣称为统计显著或总体概率。

在线留档共 433 个行请求记录，含 8 个行错误和 81 个正常返回但文字为空的行；8 个行错误使一个完整截图请求失败。3x 无候选后的条件 2x 重试，本地触发 6 次、在线 9 次，属于同一策略在不同识别输出上的正常分支，全部等待都计入耗时。

### 7.5 完整性核对

配对实验有 78 个唯一 trial，77 个完成、1 个失败。4,047 项结构检查通过：406 对共同输入行 PNG 的字节 hash 一致；检查到的 1,495 条下游置信度记录均为空，筛选候选结构、摘要参数与失败保留均符合协议。报告中的 124 个本地文件链接通过存在性检查，未发现 API key 样式泄露。

这些检查验证了流程与留档的一致性，不证明语义评分一定正确。尤其不应把 OCR 的置信度等同于翻译正确率。

## 8. 耗时定义与结论边界

主要端到端计时从已解码的 1080p 画面复制开始，包含裁剪、PNG 编码、每次新的预处理/OCR、候选筛选、摘要请求及实际发生的救援；在线也包含上传、网络和排队。它截止于得到完整可播报文本。

未计入：视频 seek/解码、真实游戏截图 API 的采集调用、模型下载及常驻初始化、TTS 合成、语音首音和播放、真实弹幕显示，以及实际发送到 LOL 的结果。早期单图表中标为“API 请求”或“OCR 已准备好”的耗时也不能冒充完整流程耗时。

本轮支持的工程判断是：在已验证的统一行图流程中，本地 OCR 适合作为低延迟候选默认后端；在线 OCR 保持可选，不能只凭接口在线/离线属性判断质量。纯多模态或 OCR 融合也应保留为 Agent 可选择的证据获取方式，而非按单一开发图结果固定为唯一方案。

更需要继续解决的是语义层的无依据推断：把“赶来时对方被单杀”变成“自己被单杀”，把省略施受者的“三次单杀”断定为发言者拿到，把对卡莎玩家的评价改成对英雄整体上分难度的评价，以及把不清的碎片猜成没闪等技能状态。替换 OCR 后端本身没有消除这些错误。

## 9. 后续验证要求

产品化前应把以下能力与研究脚本分开交付，并在演进文档中列出接口和验收标准：

1. 可由 Agent 调用的真实截图、裁剪和预处理服务，保留原图/坐标来源与显式 ROI，第一版不宣传自动聊天区域定位已经成熟。
2. OCR provider 统一结果契约与本地/在线可配置后端，缺少置信度时诚实返回未知，不能伪造等价分数。
3. 消息观察与跟踪服务，处理重复、滚动、裁切和不确定读数；识别修订与新消息区分，不能把 OCR 字形变化直接当作新消息。
4. 可注册的快捷键与可取消、可超时、可观察的触发链，Agent 可配置流程并显式选择就地模型或外部处理。
5. TTS、弹幕和发送动作的独立接口。真实合成、首音、游戏焦点和发送行为另行验收，不以本次“可播报文本”测试替代。
6. 新来源、多人/不同字号分辨率、不同 UI 缩放的留出集，以及韩语人工复核。保持输入与评分冻结，允许并记录参考争议，失败不能从分母中剔除。
