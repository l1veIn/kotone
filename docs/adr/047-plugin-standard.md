# ADR 047：Kotone 插件标准——内置插件跟本体一起改，对外只定协议；只加不改；三种做法各出一个插件再定 1.0

状态：Accepted（2026-11-27，玩家定的方向：“这两件事按你推荐的来”；细节由主会话照本 ADR 的原则定）。

修订：[ADR 043](043-plugin-shape-and-pushes.md) D1（“清单字段只给内置插件用，第三方插件没有清单”：第三方现在有一份小清单，见 D3；推送照旧不给第三方）。相关：[ADR 038](038-kotone-and-apps.md)（插件照 MCP Apps）、[ADR 045](045-automation-is-programs.md) / [ADR 046](046-programs-call-tools.md)（自动化的程序能 `push()`、`ask()`、`tool()`）、[MCP 客户端调研](../research/2026-11-24-mcp-client.md)、[2026-11-27 调研](../research/2026-11-27-dsh-and-game-plugins.md)（DSH、知名游戏工具、Coopanion）、[软件哲学](../philosophy.md)原则 11（单向门和双向门）、19（旧版本也要能读新配置）。

叫法照 ADR 039：**本体**、**插件**、**琴音**。

## 背景

调研完 DSH、GitHub 上的游戏工具和 Coopanion 之后，Kotone 的插件要主动扩充一批（调研第十节的六种做法）。玩家的话：

- “实际上我觉得可以出一个‘kotone插件标准’了，我们可以先做一批插件出来，可以直接内置kotone到项目，也可以在新的仓库。”
- “重点是，这个插件标准如果频繁更新甚至破坏性更新，带来的影响会很糟。实际上dsh和Coo的world是不是存在这种情况？这是无法避免的吗？”

### 别人的情况（2026-11-27 核对）

- **DSH**（`deepseek-ai/deepseek-harness`，0.2.3-alpha.2）：`docs/upgrade-guide` 下 0.2.x 有 18 个版本，每版一份升级指南，共 201 条不兼容变更说明（中英各一份）。插件靠 `engines.dsh` 写兼容范围自保，结果插件跟着宿主版本碎成几批。
- **Cortico / Coopanion**：Cortico 2026-09-13 建仓，2026-10-16 World 契约已是第 6 版（`EXTENSION_API_VERSIONS`，[docs/upgrading.md](https://github.com/Pal-AI-Lab/Cortico/blob/main/docs/upgrading.md)）；5 → 6 主要是改名（`console` → `webUi`、`terminal` → `console`）。之后才加“上一版经过渡层照常加载、下个大版本删”（#258）。市场里的 World 大量写着“需 Coopani 0.2.22+”“仅支持 Coopanion 0.2.12”。

**根因**：两家给插件的都是进程内的代码接口（DSH 的 `ctx` 约 120 个服务、100 个事件；Cortico 的 `WorldHost`），界面是塞进宿主网页的 JS。宿主内部一重构、一改名，插件就断；暴露的越多越难稳。而且都在 0.x 就长出了大生态。

**能不能避免**：早期的变化和底层 MCP 自己的大改（2026-07-28 版去掉了握手）避免不了；大部分破坏可以控制，取决于暴露多少、怎么演进。

## 参考了谁

| 照什么 | 来自 |
| --- | --- |
| 对外的协议不破坏，内部接口随便改，因为内部的东西在同一个仓库里一起改 | Linux：“不破坏用户空间”（系统调用）；内核树里的驱动跟着内核改 |
| 稳定的接口十年不破坏；新东西先进“提案”，只有开发版能用，定型了才进稳定版；插件写最低宿主版本 | VS Code 扩展：stable API / proposed API、`engines.vscode` |
| 行为上的改动只对声明了新目标版本的 App 生效，老 App 照旧 | Android `targetSdkVersion` |
| 协议按日期出版本、两边协商；扩展是可选的，宿主没有就当没有 | MCP（`io.modelcontextprotocol/ui` 等扩展、能力协商） |
| 上一版契约经过渡层照常加载，下个大版本才删；发布前有检查命令 | Cortico 2026-10-16 以后的做法（`pnpm check:extension`） |
| 反例：大迁移拖了几年；用宿主内部接口的外部插件每隔几个版本就断 | Chrome 扩展 MV2 → MV3；Home Assistant 的自定义集成 |

## 决定

### D1 两层：只有外层叫“标准”

- **内层：内置插件。** `plugins/<id>/`，Rust crate，依赖 `kotone-plugin-api`，和本体一起编译、一起发布。`kotone-plugin-api` 是内部接口，**不是标准**：要改就改，同一个提交里把所有内置插件一起改好（每个提交都能单独编译，照 development.md）。内置插件**留在主仓库**（玩家定的第 1 件事）。`kotone-plugin-api` 不发 crates.io、不给第三方。
- **外层：Kotone 插件标准。** 一个在任何仓库、作为**独立进程**运行的插件说的协议：MCP（工具、资源）+ MCP Apps（`ui://` 页面）+ MCP Events（SEP-3415，事件）+ 一份 Kotone 自己的小清单（D3）。别的仓库里的插件只走这个，不链接 `kotone-plugin-api`。
- 内置插件对外的那一面（英雄联盟单独发成 MCP 服务器 + App，ADR 039 D9）也算外层，照标准走。
- 为什么：外层是单向门（原则 11：第三方一旦依赖就收不回来），所以要小、要慢；内层是双向门，快改不伤人。DSH 和 Cortico 的问题是把内层直接当成了外层。

### D2 外层由三个外部标准撑着，我们只定很少的东西

- **MCP、MCP Apps 照规范**，不另起炉灶。MCP 自己的大改由宿主吸收：宿主同时支持新旧两个协议版本（`rmcp` 已兼容 2025-11-25），插件作者不用跟着动。
- **事件照 MCP Events（SEP-3415）**。服务器不支持时用观察项补（D5），事件名同一套，以后服务器支持了改成直接订阅，玩家的自动化不用改。
- **页面就是 MCP App**，不放进清单；只给页面用的工具照 `visibility: ["app"]`。
- Kotone 自己定的只有 D3 那份清单。不另定传输、不另定工具格式、不另定页面桥。

### D3 Kotone 清单（0.1 草案的字段）

| 字段 | 意思 |
| --- | --- |
| `standard` | 写这份清单时照的标准版本（最低要求），如 `"0.1"` |
| `games` | 挂在哪些游戏的配置上（游戏 id，和本体的游戏列表同一套） |
| `events` | 登记的事件：名字（`<插件 id>.<名字>`）、一句说明、数据字段；没登记的宿主不收（同内置插件的 `[[events]]`） |
| `watches` | 观察项（D5） |
| `risk` | 风险说明，一个插件一个弹窗（ADR 043） |

- 没有推送字段：推送照旧不给第三方（ADR 043 D11、“不做”）；要推由玩家的程序 `push()`。
- 没有宿主能力字段：第三方拿到的宿主能力照 MCP 客户端调研第 4.4 节，比内置的窄，这次不加。
- 清单从哪来（服务器在资源里提供一份 / Kotone 或玩家在本地写一份预设，同一个格式）在第 1 期写进标准文档时定。

### D4 只加不改（外层的规矩，照原则 19）

1. 已有字段不改名、不改含义、不加旧宿主不认识的取值；新能力用新字段。**不做纯改名**（Cortico 5 → 6 的教训）。
2. 宿主读第三方清单：不认识的字段**忽略**，在插件页的说明里列出来提示作者；缺的字段用默认值。内置插件的 `plugin.toml` 照旧 `deny_unknown_fields`（一起编译，拼错应该当场报错）。
3. 按能力协商，不靠一个总版本号：插件用到宿主没有的能力时，只那一项不可用并说明，插件其余部分照常。
4. 新东西先放进 `experimental`（字段名带这个前缀），只给内置插件或打开开发者开关的玩家；至少过一个正式版、有内置插件真用过，再转正。
5. 真要改含义，学 Android：只对 `standard` 写了新版本的插件生效，旧插件照旧。
6. 弃用：标出来以后至少保留到下一个大版本；宿主带上一个大版本的过渡层（照 Cortico）；插件页提示作者。
7. 兼容测试：CI 里固定放一组“老插件”（每个标准版本一份最小插件，加一个真实插件的快照），每次改宿主都跑。另给作者一个检查命令（照 `pnpm check:extension`、MCP Inspector），发布前自己跑。

### D5 第三方事件：订阅，或者用观察项从只读工具里产生；只进自动化

- 服务器支持 MCP Events 就订阅；不支持就用**观察项**：一个只读工具 + 参数 + 间隔 + 怎么比较 + 事件名（玩家 2026-11-27：“二次封装一个MCP壳……用来透传工具和产生事件”）。远程插件（`crates/kotone-remote-plugin`）本来就是这层壳，工具已经透传；接上给第三方的 `game_event`（`apps/desktop/src-tauri/src/remote_plugins.rs`，现在是空的）。照 Home Assistant 的 REST 传感器和 Zapier / n8n 的轮询触发，两种比较：
  - **状态变了**：取结果里一个字段，变了才发，带旧值和新值；可以写“变成某值时”。
  - **新条目**：结果是列表，按 id 去重，第一次只记底、不发。
- 只轮询玩家确认过的只读工具（注解不可信，照现有询问规则）；只对返回结构化结果的工具或有预设的工具开放；只在相关游戏开着时轮询；间隔有下限，网页接口更长；失败退避，连续失败停下并显示在插件卡片上。
- **第三方事件只进自动化**（游戏中心 → “当……的时候”），不直接进琴音的上下文、不推送；要推、要她说，由玩家的程序决定（`push()`、`ask()`）。这样 D11 不变，“事件先过自动化”这一层守住（调研第九节：这正是 Kotone 比 Cortico 多的那层）。
- 事件内容按不可信处理（剥掉看不见的字符，同工具结果）。

### D6 版本：0.x 到 1.0

- 现在是 **0.1**（草案）。0.x 期间允许破坏，但每次都写进标准的变更记录，宿主照样读上一个 0.x（一版过渡）。
- **1.0 的条件**（玩家定的第 2 件事）：三种做法各有至少一个插件跑通、真机验证过——
  1. 自己做：照知名工具做的游戏插件（云顶之弈或 CS2）；
  2. 驱动现成工具：原神（BetterGI）；
  3. 远程 MCP + 观察项：绝区零一条龙；
  
  并且至少一个插件在别的仓库、只靠外层协议跑通。满足后冻结 1.0：之后 1.x 只加不改，破坏只能进 2.0，2.0 带 1.x 的过渡层。
- 1.0 的标准文档、检查命令、老插件测试缺一样都不发。

## 不做

- 不把 `kotone-plugin-api` 给第三方；不做进程内的第三方插件（JS、DLL、WASM）。
- 不兼容 DSH、Cortico 的进程内接口（“从 DSH 导入” MCP 服务器和技能照调研第二节，可以做，不属于本标准）。
- 推送照旧不给第三方；第三方事件不直接进她的上下文。
- 不做纯改名的版本。

## 有多深远

- 外层（协议 + 清单 + D4 的规矩）是单向门：第三方插件一旦依赖就收不回来。0.x 是唯一能便宜地改的窗口，所以 1.0 的条件写死在 D6。
- 内层是双向门：内置插件和 `kotone-plugin-api` 随本体一起改。
- “第三方事件只进自动化”是给第三方的权力，单向门：以后放宽可以（比如允许某类事件进她的上下文），收紧很难。

## 分期

| 期 | 做什么 | 玩家看到的 |
| --- | --- | --- |
| 1 | 写标准文档 `docs/plugin-standard.md`（0.1：外层协议、清单字段、清单从哪来、D4 的规矩、变更记录）；清单的读取（不认识的字段忽略） | 没有界面变化 |
| 2 | 远程插件的观察项 + 第三方事件进自动化；绝区零一条龙的预设 | 第三方插件页多一块“事件”；自动化的“当……的时候”能选它的事件；一条龙跑完能推一行（用模板） |
| 3 | 内置插件：云顶之弈或 CS2（自己做）、原神（驱动 BetterGI） | 新的插件卡片 |
| 4 | 检查命令 + 老插件兼容测试进 CI；一个别的仓库的插件 | — |
| 5 | D6 的条件满足 → 1.0 | — |

## 怎么定的

主会话的建议（2026-11-27）：两层，内置插件留主仓库，别的仓库的插件只走协议；标准先叫 0.x，三种做法各做出一个插件再定 1.0；外层只加不改。玩家：“可以，写 ADR 吧。这两件事按你推荐的来。”第三方事件的做法（观察项、只进自动化）来自同一天的讨论（调研第十节）。
