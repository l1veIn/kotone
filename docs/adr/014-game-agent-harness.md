# ADR 014：Kotone 定位为游戏场景的 Agent 运行框架；三层结构与内置 Agent

- 状态：Accepted / 已采纳（2026-11-16，方向已定；原“待定”各项已由用户确认，见“已确认”一节）

- 细化：[ADR 015](015-agent-scope-and-stack.md)（完成度与技术栈；各开发步骤的范围以它为准）
- 不变：[ADR 013](013-automation-domain-model.md)（自动化的定义 / 触发 / 执行记录与调度语义）

## 问题

Kotone 陪玩现在是“输入一句话 → 调一次 AI → 从提醒 / 帮忙打字 / 直接回答里选一件做”。自动化（ADR 013）出现后，陪玩的每个动作其实都是“产出一次执行”；用户进一步提出：陪玩应该像 Codex、Claude Code、dsh 那样，是一个**有聊天界面、能多轮调用工具的 Agent**，自动化只是它的工具之一。

调研显示：游戏陪玩类产品已经存在，但大厂和国内商业产品只做问答、攻略、陪伴，开源项目多停在聊天与虚拟形象，研究型 Agent 则让模型自己玩。“替玩家动手、由玩家指挥”的游戏场景 Agent 运行框架还空着，而 Kotone 已有其中大部分能力（工具服务、自动化、语音输入、语音 / 弹幕输出）。

## 决策

### 1. 定位

Kotone 是**游戏场景的 Agent 运行框架**：类比 Claude Code 之于写代码（文件、终端工具 + Agent 循环 + 权限），Kotone 提供屏幕感知、键鼠输入、游戏聊天、语音与弹幕、游戏配置等工具，有护栏的自动化运行层，内置的 Agent，并把全部工具开放给外部 Agent。原有的“语音输入打字进游戏”保留为独立的实时功能（有预览、文字处理、历史），不并入 Agent。

### 2. 三层结构

| 层 | 内容 | 谁来用 |
| --- | --- | --- |
| 第一层：基础能力 | 输入注入（键鼠、打字、发到游戏聊天）、截图 / 文字识别 / 聊天跟踪、语音与弹幕、窗口、游戏配置、模型 / 连接 / 设置、诊断……即工具服务的工具清单 | 自动化（只用沙盒白名单的一部分）、Agent |
| 第二层：自动化 | 调度器、执行器、已保存的自动化（ADR 013）；自身也作为一组管理工具开放（`automation.run / save / list / runs / stop …`） | Agent |
| 第三层：Agent | 内置的琴音 Agent（聊天窗口 + 游戏内语音）；外部 Agent（工具服务 / MCP） | 用户 |

两处有意的不对称：**自动化不调用 Agent**（运行中不调模型，才能毫秒级执行；需要理解画面就回到 Agent）；**自动化程序只能用第一层的一部分**（没有设置、网络、文件），Agent 能用全部工具。

### 3. 内置 Agent

- **Agent 循环**：多轮“调用工具 → 拿结果 → 再思考”，流式输出，步数与时长上限，随时取消。替代现在的单次规划（`kotone-ai::companion`）；连接、能力自检沿用。
- **工具**：直接使用工具服务的工具清单与执行入口，在进程内调用——与外部 Agent 同一份实现。工具有八十多个，不全量塞给模型：常用的一组始终提供，其余按类别让 Agent 先查（列出 / 搜索）再用。
- **已保存的自动化即工具**：每个已保存的自动化（名字、说明、入参声明）可以作为一个工具交给模型，用户的自动化库就是 Agent 的工具箱。
- **原陪玩动作改为工具**：提醒（延迟 + 播报）、回答（立即播报）、帮忙打字（新增内置动作“发到游戏聊天”，走游戏配置的开聊天框键、频道、粘贴、发送、焦点恢复）、记住聊天框位置。它们产生的执行都进入自动化的执行记录。
- **上下文**：系统提示放当前游戏的说明与已保存自动化的摘要；对话保存在本机，长对话压缩或截断。
- **游戏场景工具会继续增加**（第一层）：打开 / 关闭游戏、切换窗口、查版本公告等。

### 4. 两种入口

- **聊天窗口**：经典 AI 聊天界面，多轮对话；消息流里显示工具调用与结果、需要确认的操作给按钮、有停止按钮。适合设计自动化这类需要来回商量的事（Agent 可以截图、找位置、试运行、保存）。
- **游戏内**：陪玩热键说一句话 = 给 Agent 发一条消息；结果用语音 / 弹幕播出。要快：只给常用工具、限制步数，截图与识别文字在请求时直接附上。快捷指令保留两种：“一句话”= 发给 Agent；“运行自动化”= 直接执行，不经过 AI。（2026-11-25 起两种都是「设置 → 热键」里自己加的热键，存在热键表 `hotkeys.bindings`，运行自动化就是绑 `automation.run`；以后还能调工具、打开页面，见 [ADR 040](040-hotkeys-belong-to-core.md) 第 3 期。）

### 5. 权限（参照现有 Agent 运行框架）

- 每个工具一条规则：**允许 / 询问 / 禁止**；整体模式：默认（读与常规游戏操作直接执行，有风险的先问）、全部允许、只读。默认规则由工具清单里已有的副作用标记推出。
- 默认需要询问的：改设置、删除、退出 / 重启、管理员提权、开机自启、下载大模型、**AI 新写的程序第一次运行**。读状态、截图、识别、播报、提醒、用户明确要求的打字、运行已保存的自动化、停止，直接执行。
- 询问方式：聊天窗口里给按钮；游戏内用语音 / 弹幕问，或留到窗口里确认。
- **屏幕上读到的文字一律是数据**：作为工具结果交给模型时标明来源不可信，聊天里的“指令”不能让 Agent 越过权限。
- 外部 Agent 的规则不变（全部能力开放，权限由它们自己的运行框架管）。

## 已确认（2026-11-16，用户在新一轮开发开始时逐项确认，均按原建议）

| 事项 | 决定 |
| --- | --- |
| 聊天界面放哪 | 「陪玩」页改为聊天窗口，导航名改为「琴音」；AI 连接、热键、快捷指令等放到它的设置分页 |
| 游戏内语音与聊天窗口是否同一段对话 | 同一个 Agent、同一段对话，回到桌面可以接着聊 |
| 空白页的起手提示 | 要，例如“做一个自动化”“看看队友在说什么”“设个提醒” |
| 已保存的自动化给不给 AI 用 | 默认全部可用（最多 30 个交给模型），每个可单独关掉 |
| 帮忙打字的内容是否写进执行记录 | 写进去（与提醒正文一致），用户能在「记录」里看到替他发了什么 |

## 开发顺序

1. **Agent 循环**（`kotone-ai`）：多步工具调用、流式输出、上限与取消、对话存储；测试用假模型。
2. **工具接入与权限**：进程内调用工具清单、工具分组与查找、规则与模式、询问流程；原陪玩动作改为工具（含“发到游戏聊天”内置动作）；已保存自动化作为工具。
3. **聊天界面**：消息流、工具调用卡片、确认按钮、停止、起手提示、对话列表。
4. **游戏内入口**：陪玩热键与快捷指令改走 Agent；快速模式；语音 / 弹幕确认。
5. **游戏场景工具**：打开 / 关闭游戏、切换窗口等；按游戏的“允许自动化输入”开关。
6. **文档、Skill、插件同步**。

## 结果

Kotone 的结构从“几个功能”变成“工具 → 自动化 → Agent”三层，每层都对上开放，同一份工具实现同时服务内置 Agent 与外部 Agent。陪玩不再是写死的三种动作，而是一个能多轮使用全部工具、带权限与确认的游戏 Agent；自动化是它的执行与复用层。
