# ADR 015：内置 Agent 的完成度与技术栈

- 状态：Accepted / 已采纳（2026-11-16，用户确认：按“第一版”一列做、不带 Node、走路线 A；同日修订：模型通信层改用 rig-core，见 §2）
- 细化：[ADR 014](014-game-agent-harness.md)（内置 Agent 的定位、三层结构与权限）；开发顺序沿用 ADR 014，每一步的范围以本 ADR 为准
- 参考：[游戏陪玩 Agent 现状调研](../research/2026-11-16-game-agent-landscape.md)

## 问题

ADR 014 定了“做一个内置的游戏 Agent”，没有定**做到什么程度**、**用什么搭**。成熟的 Agent 产品（Codex、Claude Code、办公类 Agent，以及精简的开源底座 pi）功能分很多层：模型接入、循环、工具、权限、上下文与记忆、扩展、入口、评测、开放。每层都可以做得很深。技术栈取决于哪几层必须 Kotone 自己写、哪几层可以借现成的，所以要先定完成度。

第 1 步开工时，Agent 循环已经在 Rust 里自己写了（`kotone-ai::agent`，提交 `428bd858`），这是在技术栈确认之前做的。本 ADR 补上这个决定。

## 决策

### 1. 完成度：对标 pi 的“精简但完整”，游戏相关的层做深

| 层 | 游戏场景的差别 | 第一版 | 以后 | 不做 |
| --- | --- | --- | --- | --- |
| 1 模型接入 | 截图看图是主要输入；首字要快；国内服务商为主 | OpenAI 兼容接口、流式、工具调用、推理内容带回、**看图**、**用量统计** | Claude / Gemini 原生接口、提示缓存 | — |
| 2 循环 | 玩家会在 Agent 干活时又按热键说话；游戏内要快 | 多步、上限、取消、**插话与排队**、**快速模式** | 并行执行工具 | — |
| 3 工具 | 屏幕、键鼠、聊天、语音、自动化；自动化会在 Agent 空闲后才跑完 | 进程内调用工具清单、分组与查找、结果可带图片、**自动化完成事件回到对话** | 第三方工具声明（类似 G-Assist 插件 manifest） | — |
| 4 权限 | 输入不可撤销且有时效；游戏内用语音确认；按游戏的“允许自动化输入”开关 | ADR 014 §5 全部 | — | — |
| 5 上下文与记忆 | 游戏说明相当于项目说明；对话多是短指令 | 系统提示拼装（游戏说明、已保存自动化摘要）、按预算截断、对话列表 | 长对话压缩摘要、玩家偏好的长期记忆 | 会话分支 |
| 6 扩展 | 一个游戏一个“游戏包”（说明 + 自动化 + 提示） | 不做 | Skill，采用通用的 `SKILL.md` 格式 | 子 Agent、插件市场 |
| 7 入口与交互 | 玩家注意力在游戏上，回复要短 | 聊天窗口（ADR 014 §4）+ 游戏内语音 / 弹幕 + 快捷指令 | 主动触发（如队友发消息时主动提示） | — |
| 8 评测与诊断 | 固定场景：截图 + 指令 → 期望的工具调用 | 对话与执行记录可回看、能力自检 | 场景评测集 | — |
| 9 开放 | 工具已经通过工具服务 / MCP 开放 | 已有 | 聊天窗口作为 ACP 客户端接外部 Agent | — |

### 2. 技术栈：路线 A，全部在 Rust 里

- **Agent 循环、模型接入、对话存储都在 `kotone-ai`（Rust）**，和工具服务、自动化在同一个常驻进程里。理由：
  - 工作量的大头是第 3、4、7 层加自动化，只能 Kotone 自己写，而且已经是 Rust；
  - 游戏内入口要常驻、要快，不能依赖设置窗口开着，也不想多一次跨进程调用。
- **不带 Node 运行时**，因此不用 pi 当运行时。pi 作为功能清单与设计参考（插话 / 排队、会话、压缩、Skills 的做法）。
- **模型通信层用 `rig-core`，循环自己写**（同日修订；最初的决定是“暂不引入 rig”）：
  - `rig-core` 实现 `ModelClient`（`agent/model.rs`）：负责各家的流式格式与工具调用拼装、推理内容带回（DeepSeek 等）、图片编码、用量统计、按模型价格表估算费用，以后接 Claude / Gemini 原生接口也在这一层；
  - **不用 `rig-agent`**：取消、整轮时长上限、插话与排队、“每个调用都有结果”、权限询问都要放进它的钩子里写，省不了多少代码，而且它变得最快；
  - 版本钉死（`=0.46.0`）；Kotone 的消息格式、存盘格式、事件都不依赖 rig 的类型，rig 只出现在 `agent/model.rs`，升级时只改这一个文件；
  - **不引入 aws-lc**：rig-reqwest 的 `rustls` 特性会带进 aws-lc（C 加密库，要 cmake 编译）。改为关掉该特性，自建 reqwest 0.13 客户端，进程默认加密提供者装 `ring`（与 Kotone 其余部分一致），再交给 rig；
  - 实测（2026-11-16，rig-core 0.46，同一个最小程序，发布构建，两边都用 ring）：exe 5.29 → 8.84 MB（+3.5 MB），gzip 后 2.18 → 3.29 MB（+1.1 MB），依赖包 158 → 193 个。增量主要是它不能按需关闭的各家服务商代码；
  - 已知差异：rig 把系统提示编码成文字片段数组（`[{"type":"text",…}]`），对所有 OpenAI 兼容服务商都如此、不能配置；各家是否都接受，要在真实服务商上核对（花费需用户同意）。

### 3. 边界上用标准，方便以后替换或接入

| 边界 | 标准 | 现状 |
| --- | --- | --- |
| 工具 | MCP / 工具服务 | 已有；内置 Agent 在进程内调同一份实现 |
| 扩展 | `SKILL.md` 格式的 Skill | 以后做；不自创格式 |
| 聊天窗口 ↔ Agent | 事件模型照 ACP 的会话更新设计：消息片段、工具调用及其状态、权限请求一一对应 | 第 3 步（聊天界面）按此设计；以后接外部 ACP Agent 时只是加一种来源 |

### 4. 对 ADR 014 开发顺序的补充

第 1 步已有：多步工具调用、流式、步数 / 时长 / 单步调用数上限、取消、不可信数据隔离、上下文截断、对话存储。按本 ADR 补充的内容：

- **第 1 步补**（已完成）：用户消息带图片（截图；只有本轮带图，存盘不存图）；用量统计（每次模型调用的输入 / 输出 / 缓存 / 推理 token，价格已知时带费用）；插话（运行中收到新消息：当前工具执行完后交给模型，本步剩下的工具调用不执行）与排队（本轮结束后由调用方开始新的一轮）；事件模型对齐 ACP。
- **第 2 步加**：工具结果可带图片；自动化执行结束（`automation.finished`）作为一条消息回到发起它的对话。
- **第 4 步**：快速模式（工具子集、更低的步数上限、预先附上截图与识别文字）。

## 考虑过的方案

- **路线 B：pi 当底座（另起 Node 进程）**。第 1、2、5、6 层基本现成。不选的原因：
  - 安装包要带 Node 运行时（用户不接受）；
  - 两种语言，工具要跨进程调用；
  - 工作量的大头（第 3、4、7 层）不会因此减少；
  - 另外，按已知版本 pi 有意不内置权限确认，要靠扩展实现（未核实最新版本）。
- **路线 C：聊天窗口只认 ACP，内置 Agent 作为其中一个**。现在不做。内置 Agent 本身仍要按 A 或 B 来写，而外部 Agent 走游戏内快速模式会慢。§3 的事件模型对齐让它以后可以作为加法实现。
- **rig 的 Agent 运行时（`rig-agent`）**。没有选：0.x 版本，接口变化快，例如工具 `call` 的签名刚加了 `ToolContext`、Agent 运行时刚拆成独立的包；而且 Kotone 的权限询问、取消、动态工具集都要放进它的钩子里，能否满足没有核实。

## 结果

内置 Agent 的范围与技术栈都定了：Rust 单进程，第一版对标 pi 的精简完整度，游戏相关的工具、权限、入口做深；会话分支、子 Agent、插件市场不做。模型层与对话存储都在接口后面，标准化的边界（MCP、`SKILL.md`、ACP 式事件）为以后接入外部 Agent 和扩展留了位置。
