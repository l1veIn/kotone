# ADR 040：快捷键归本体——插件只登记命令，一张表、一个地方改

状态：Accepted（方向，2026-11-25，玩家：“可以，你这套很清晰”）/ 第 1 期做完（2026-11-25，见末尾实施记录；界面上这一页叫「设置 → 热键」，照术语表不叫“快捷键”）/ 第 2 期第 1–3 步做完，第 4 步（删主键位）等真机脚本和真人按完再做（见实施记录“第 4 步的准备”）/ 第 3 期做完（快捷指令搬进表；调工具、打开页面和绑的时候问权限；「设置 → 热键」里自己加；英雄联盟一键喊话的四条预设 = ADR 041 第 3 期，见实施记录）。

2026-11-28 修订（[ADR 052](052-retire-reminder-assistant.md)）：D10 了结——0.1.x 的提醒助手退掉了，它的键（`legacy-reminder`）一起去掉：热键表里没有这一行、不登记、没有按住的分派；升级用户的呼叫键不再存在 `assistant.companionBindings.hotkey`，所有人都是 `assistant.hotkey`（热键表 `kotone.call` 的镜像）。下文实施记录里提到提醒助手热键、`companionBindings` 的是当时的样子。

## 背景

玩家（2026-11-25）：

- “有一个东西我心里觉得不太舒服，就是‘快捷键’，实际上，现在整个项目里有非常多的快捷键，它们分散在各个地方甚至插件内部。我在想，插件有自己的快捷键，陪伴智能体也有自己的快捷键，迟早有一天，这个快捷键的数量会多到记不清在哪。”
- “这应该不是我们这个项目独有的问题吧？……社区里成熟的方案是什么呢？”

清点的结果（[共享资源评估](../research/2026-11-25-shared-resources-audit.md)，只读代码）：

- 底层已经只有一份：一个低级键盘钩子线程、一个 `HotkeyManager`（`apps/desktop/src-tauri/src/hotkey.rs`），前端一个冲突检查覆盖 16 个可设置的键。
- 设置散在 7 个以上的地方：
  - 插件 → 语音输入（语音输入热键，加频道切换、重发、文字处理开关、切换文字处理流程 4 个）；
  - 游戏陪玩 → 角色 → 唤醒（呼叫键、8 个快捷指令）；
  - 设置 → 模型 → 语音识别（启动热键）；
  - 设置 → 系统（停下热键、热键实现）；
  - 旧的提醒助手。
- 插件接口里没有快捷键。语音输入的 5 个键在本体的 `Settings`、桌面端、命令行里分别写死；新插件（包括第三方 MCP App）想要一个键只能改本体。
- 快捷指令是 8 个固定格子，自动化只能经它绑键；ADR 038 写了“热键”可以触发自动化，没做。
- 冲突检查不看游戏的聊天键、控制台触发键（F23）、Esc，插件不参与。
- 没有一处列出全部快捷键。

## 参考了谁

| 做法 | 谁 |
| --- | --- |
| 动作和按键分开：插件登记命令，不直接抢键 | VS Code 的 commands、Obsidian 的 `addCommand`、Raycast 的 command |
| 一个地方列出全部，标来源，用户在这里改 | VS Code 的“键盘快捷方式”编辑器、Obsidian 的“设置 → 快捷键”、Raycast 设置里的扩展页 |
| 插件不带默认键，只有宿主自己有极少的默认键 | [Obsidian 插件指南](https://docs.obsidian.md/Plugins/Releasing/Plugin+guidelines)（“避免给命令设默认快捷键”，有 lint 规则 `no-default-hotkeys`）；[Raycast](https://manual.raycast.com/command-aliases-and-hotkeys) 的键由用户设，默认只有打开 Raycast 的那一个 |
| 绑的时候查冲突 | Obsidian 标红；VS Code “显示相同按键绑定” |
| 少记键：一个键唤出入口再选 | Raycast、VS Code 命令面板；Kotone 的对应物是呼叫键加一句话（ADR 029：“玩家只要一个 Key 和一个呼叫键”） |

## 决定

**D1 命令和按键分开。** 插件在 `plugin.toml` 里登记命令：id、名字、一句说明、类型（按一下 / 按住，按住的有“按下”和“松开”两个阶段）。命令有三种（修订 2026-11-25：“插件自己处理的动作”经 `AfterHearing::command` 调，见实施记录）：

- 插件自己处理的动作（例如语音输入的“说话”）：宿主在按下 / 松开时调插件；
- 调一个工具，可以带固定参数（例如英雄联盟的“一键喊话”就是调发到游戏的工具）——第 3 期落地：`[[commands]]` 写 `tool` + `args`，只能调插件自己给她的工具，英雄联盟的四条预设调 `lol.shout`（见实施记录第 3 期第 4 步）；
- 打开一个页面（`ui://…`）。

第三方 MCP 服务器不用新协议：它的每个工具、每个 `ui://` 页面都可以被绑成命令。本体自己的动作（呼叫、停下、开关语音识别……）也登记成命令，和插件的一样出现在表里。

**D2 一张表。** 设置 → 通用 → **快捷键** 一页，列出全部：本体的、每个插件的、玩家自己加的；可以搜索；每行标来源（本体 / 插件名 / 自己加的）；冲突标红。Esc 这类固定的键只读列出。往游戏里按的键（聊天键、控制台触发键）不是快捷键，不在这张表里改（照旧在游戏配置里），但参与冲突检查。

**D3 只在这里改。** 别的页面（语音输入、唤醒、停下……）只显示当前的键和一个“去改”的链接。例外：第一次打开时的引导照旧可以设呼叫键，写进的是同一张表。

**D4 默认键只有三个。** 本体的呼叫键、停下热键；内置插件里只有语音输入的“说话”（CapsLock）——输入法的键就是它本身。其余命令、所有第三方插件都不带默认键。**已经有的绑定不收回**：老用户现在设着的键（包括频道切换现在默认的 Shift+CapsLock）迁移进表里照旧生效，只是新装的不再默认带。

**D5 快捷指令并进表里。** 8 个固定格子去掉，变成表里的“加一个快捷键 → 选要做的事”：说一句话、运行某个自动化、调某个工具、打开某个页面。现有的 8 个迁移进表。这也补上了 ADR 038 里“热键触发自动化”。

**D6 冲突只在后端查一次。** 冲突检查挪到本体（后端）一处，前端只显示结果。范围：本体的、插件的、玩家加的键，所有游戏配置里的聊天键和控制台触发键，Esc；照旧提示“这个键游戏里常用”（`hotkeys.conflicts`）。

**D7 插件不碰按键。** 插件接口加“命令”的登记和回调，不加“注册快捷键”。全进程的键盘钩子照旧只在宿主（ADR 038，已有边界测试）。本体 `Settings` 里语音输入专用的快捷键字段去掉，改成表；命令行读同一张表。（修订 2026-11-25：第 2 期旧字段先当表的只读镜像，磁盘上一直照表写全，见实施记录。）

**D8 存法。** 设置里一个 `hotkeys.bindings` 列表，每条：键、命令（`<来源>.<命令 id>`，或工具名加参数，或页面地址）、按一下 / 按住。读旧写新、不覆盖新字段（同插件重构的迁移）。（修订 2026-11-25：不存“按一下 / 按住”，由命令自己声明，见实施记录。）

**D9 权限在绑的时候问。** 给一个有副作用的工具绑键，绑的时候照工具的权限问一次（说明这个工具会做什么），按键时不再问——游戏里按下去再弹确认没法用。只读的工具不问。

**D10 旧提醒助手的键** 照旧，等 0.1.x 的提醒助手退掉时一起去掉，不在本 ADR 里做。（2026-11-28 已去掉，见 [ADR 052](052-retire-reminder-assistant.md)。）

## 不做

- 按场合换键（VS Code 的 `when`）、组合序列（先按一个前导键再按一个）、每个游戏一套键：等真有需要。
- 插件自己弹的“设一个键”的界面。

## 实施记录

- **2026-11-25 快捷指令的键改了立即生效**（[共享资源评估](../research/2026-11-25-shared-resources-audit.md)第二节第 13 条）。复现：单元测试 `settings_cmd::hotkey_settings_tests::changing_a_quick_message_hotkey_requires_registration`，给快捷指令绑键、换键，判断函数都说“没变”，语音识别开着时不重新登记。界面上的样子：这一格原来没绑键时提示“已保存，语音识别准备好后生效”（识别明明开着）；原来绑着键时提示“已保存并生效：<旧的键>”，按新键没反应。修法：`hotkey_registration_changed` 比较 8 个槽位各自登记的键（照 `hotkey.rs` 的 `named_list_from`：第 n 条占 `quick-message-n`，没有这一条就是空的），键变了、加了一条带键的、删了一条（后面的挪了格子）都立即重新登记；加一条没绑键的、只改说的话或自动化的入参不重新登记（按下时才读那一格）。修完以后“……后生效”只在语音识别还没开始时出现。没做本 ADR 的第 3 期（快捷指令并进快捷键表）。
- **2026-11-25 第 1 期：冲突只在后端查一次，「设置 → 热键」只读列出全部**（D2、D4、D6）。复现：Playwright `apps/desktop/e2e/hotkeys-page.spec.ts` 第一条，在唤醒页把呼叫键设成 Enter、Shift+Enter（英雄联盟的开聊天框键）、F23（带控制台通道的游戏配置）、Escape，改之前 4 个都直接保存、没有提示（前端 `findHotkeyConflict(settings, "assistant", key)` 对这 4 个都返回 null，它只比 16 个可设置的键）。修法：表和冲突的规矩只在 `crates/kotone-core/src/hotkey_table.rs`（修饰键加主键相同算冲突；Esc 不看修饰键，因为录音时按 Esc 取消、她操作游戏时按 Esc 停下都不管修饰键）；范围是本体的键、语音输入的 5 个、快捷指令、Esc、所有游戏配置的打开聊天框键 / 各频道的开框键 / 发送键 / 控制台触发键（同一个游戏里键相同的算一条，正在用的游戏排前面）；0.1.x 只用语音输入的人没有呼叫键、停下热键、快捷指令，插件关着时它的键照样参与检查（打开插件就会撞上）。桌面端 `hotkey_table_cmd.rs` 给 `get_hotkey_table`、`check_hotkey`（原来的 `detect_hotkey_conflicts` 并进来：同一次给冲突和“这个键游戏里常用”的提示）；前端的 `findHotkeyConflict`、`combosConflict` 删掉，改键的各处（热键输入框、新手引导、语音输入页和它的引导）改调 `checkHotkey`，提示的字不变。「设置」多一个分页“热键”（不叫“快捷键”：术语表里它是不说的词），每行标来源（Kotone / 插件名 / 自己加的 / 固定），冲突标红并写和谁冲突，“去改”用设置说明里的位置跳到现在改它的页面；表里每项的字段和位置有测试对着 `settings_guide.rs`，宿主登记的每个热键都要在表里（`hotkey.rs` 的测试）。她和外部 Agent：`hotkeys.status` 多了 `bindings`、`gameKeys`，`hotkeys.conflicts` 多了 `conflicts` 和可选入参 `except`，没加新工具名。还没做（第 2 期）：`HotkeyManager` 登记时的冲突（同一个键谁先登记）、命令行（`kotone-cli`）各自的检查照旧；`settings.update` 不拒绝冲突的键，Agent 要先查 `hotkeys.conflicts`。
