# ADR 027：0.1.x 到 0.2.0 的过渡

状态：0.1.14 已发布（2026-11-19）。0.2.0 候选的发布与放量仍待玩家确认。

## 更新器核实

- 0.1.13 的设置窗口挂载约 3 秒后检查一次，「关于」可手动检查。两个入口都直接调用插件的 `check()`，只提示，用户点安装才下载。固定地址依次为腾讯云 COS 的 `releases/latest.json` 和 GitHub 的 `releases/latest/download/latest.json`。有效清单决定结果，HTTP 204 直接表示无更新。没有分桶、客户端 ID 或版本模板。因此改任一旧地址会影响所有命中它的旧客户端，提示发生在各自下一次检查时。[0.1.13 设置窗口](https://github.com/l1veIn/kotone/blob/v0.1.13/apps/desktop/src/routes/settings/Settings.svelte#L142) · [0.1.13 更新源](https://github.com/l1veIn/kotone/blob/v0.1.13/apps/desktop/src-tauri/tauri.conf.json#L96)
- 两版锁定的 `tauri-plugin-updater` 为 2.10.1。可在 URL 中用 `{{current_version}}`、`{{target}}`、`{{arch}}`、`{{bundle_type}}`；静态路径只能按这些属性区分，用不了本机随机桶。Rust 可覆盖本次检查的地址、读取 `Update.raw_json`、使用自定义比较器并调用原签名校验的下载安装流程。本方案选独立地址与本机判断，不向服务器发桶号或账号。[Tauri 更新器](https://v2.tauri.app/plugin/updater/) · [2.10.1 检查实现](https://github.com/tauri-apps/plugins-workspace/blob/updater-v2.10.1/plugins/updater/src/updater.rs#L413)
- 插件默认只接受 SemVer 严格大于当前版本的更新。固定版本提供 Rust 比较器和 JS/Rust 命令的 `allowDowngrades`，Kotone 的正常检查没有启用。切低清单版本只能阻止后续升级，已升级的用户通过手动重装回退。[2.10.1 命令](https://github.com/tauri-apps/plugins-workspace/blob/updater-v2.10.1/plugins/updater/src/commands.rs#L49)

## 通道、备份和回退

1. 旧 COS `latest.json` 与 GitHub 的稳定 latest 始终给仍会访问这两个地址的旧客户端提供 0.1.x。先让 0.1.13 正常升级到 0.1.14。旧客户端完全不认识 `rolloutPercent`，即使 COS 正常，也不能把 GitHub fallback 指向 0.2.x。
2. 0.1.14 优先检查 0.1.x 维护更新，再读独立的 COS `latest-0.2.json`。本机随机保存 0–99，桶号小于整数 `rolloutPercent` 才提示该 0.2 更新。字段缺失、格式错误、地址不可用均保守放行旧版维护源。安装前再确认候选与分桶仍有效。0.2 的后续更新也使用独立地址。
3. 下载安装前生成 `<KOTONE_HOME>/backup/<版本>-<时间>/` 快照。只复制应用数据目录，排除递归备份目录。系统凭据、外置模型和历史目录以及 WebView2 用户数据由原位置管理。复制失败应停止安装。插件的退出钩子没有可返回的错误，因此由 Rust 命令在下载前备份、验签后复核放量，再启动安装，前端没有直接安装权限。手动回退从「关于 → 回到旧版本」打开 0.1.x 安装包。先退出应用，留一份当前数据，按需从备份恢复。正式发布的 0.1.13 本身没有灰度与备份功能。
4. 在候选分支限制自动发布工作流和 COS 旧通道只处理 0.1.x。0.2.0 后续经确认制作签名安装包、核对校验和、保留 GitHub 旧 latest，单独准备 COS 灰度清单。0.2 草稿不带旧源名的 GitHub `latest.json`。批准后如果公开 0.2 GitHub 资产，API 必须显式带 `make_latest: "false"`，并重新核对两条旧地址仍返回 0.1.x。发布前还须确认默认分支的手动 COS 发布入口已部署同一护栏，因为该入口与候选 Tag 分开运行。离线脚本只生成文件，实装路径、签名和开关仍须在发布前验收。0.1.13 直接手装 0.2.0 时，先保留旧目录快照。计划中的自动路线经过 0.1.14。[GitHub Release API](https://docs.github.com/en/rest/releases/releases#update-a-release)
5. 看 [过渡验证报告](../research/2026-11-19-upgrade-validation.md) 了解哪些步骤是源码/夹具证据、哪些在隔离真机执行。未经玩家确认，不合并、不发版、不打标签，也不更新公开清单。

## 0.1.14 独立验收

0.1.14 保留原有录音和提醒热键、识别模型及数据位置。配置新增一个默认关闭的录音降音量开关。Dota 2 适配、删除记录、本机分桶和备份均使用独立文件。WebView 实际渲染故障时，悬浮窗会关闭并记住该状态。自动备份从 0.1.14 发起下一次更新时开始生效。

维护版可用一份代表性的合成旧配置做隔离覆盖安装，检查原录音键、识别设置和语音输入基本流程，并核对发布制品的更新签名与清单。灰度边界、备份和回退入口已有自动化测试。多份真实匿名配置、跨到 0.2.0 的安装与回退链、真实游戏及三款杀软验证留在 0.2.0 放量验收。

## 老用户升级差异与决定

| 项 | 0.1.13 的行为及 0.2 风险 | 决定 |
|---|---|---|
| 录音、发送和频道热键 | 自定义快捷键、按住/点按、发送与预览语义可能被新引导重选 | **保持原样**，不由升级引导写入。 |
| 模型、连接、麦克风和 VAD | 旧模型、引擎选项、外置模型目录、连接、麦克风和 VAD 均能在老配置自选。新用户路径会尝试选择 DeepSeek ASR/OCR | **保持原样**。升级时选择认识琴音只配置新的对话连接和呼叫键，不改旧 ASR、提醒助手连接或活动游戏。 |
| 语音发送与历史 | 游戏聊天按键、渠道、热词、历史记录策略、录档和音效提示是语音输入法原有数据 | **保持原样**。使用同一目录和原有字段，现有英雄联盟热词删除记录继续生效。 |
| `~` 呼叫键 | 0.2 曾自动补 `Backquote`，低层钩子完全命中会吞键 | **必须改**。旧配置缺键时留空。原先显式绑定的提醒键继续作提醒用途。玩家在“认识琴音”里自己设置呼叫键并看到按键冲突提示。原来未绑定 `~` 的配置要验前台能收到该键。 |
| 旧提醒助手快捷键 | 0.1.13 的对讲机按住/松开，录音笔/一句话按各自模式。0.2 的呼叫键是点按 | **保持原样**。旧提醒路由、按键语义、设置、连接和列表在启用琴音之后仍保留。琴音的呼叫键和连接独立保存，同一个热键不能用于两条路径。 |
| 等待中的提醒和历史 | 旧 `reminders.json` 有 ID、内容、到期、播报和过去记录，新调度文件不同 | **保持原样**。迁移保留 ID、原截止时间和交付选项，遵循原有宽限和最多一次规则。保留旧文件以便回退，回退如使用旧快照须留意宽限内已播的提醒。 |
| 首次打开、首页及导航 | 已有配置的用户可能被新引导拦住，入口移动到琴音页面 | **必须改**。识别旧配置跳过新首启，首页仍为语音输入，保留游戏适配、历史和提醒入口。一次性先显示“语音输入法的用法没有变”，默认按钮“继续只用语音输入法”，另一项“认识琴音”。随时可重新选择。 |
| 气泡、唤醒、游戏语音、自动复盘 | 0.2 新增或按新配置默认启用的主动行为 | **必须改**。旧用户的旧提醒展示保持，新的提示、后台唤醒、自动复盘等在明确启用琴音前保持安静，不自动安装虚拟声卡。 |
| DeepSeek 语音“自动” | 若已有 DeepSeek 连接，自动选择会把旧提醒的系统语音变为远程语音 | **保持原样**。旧提醒的系统/本地语音与琴音独立，启用琴音后仍按旧设置播报。已有付费识别或提醒连接仍按旧设定计费。 |
| 内置技能与自动化 | 新版会在启动写入内置程序和工作区 | **必须改**。老用户未启用琴音时不新增这些默认安装。已有提醒及其调度保持。 |
| 游戏列表检测 | 新列表页会查已安装游戏 | **必须改**。旧模式显示游戏适配，保留手动选择和编辑，不自动检测已安装游戏。 |
| Dota 2 与降音量 | 0.1.14 给旧输入法带入这两项。直接沿用 #18 的 Dota 2 恢复出厂会让用户删不掉 | **必须改**。两个版本用同一 Dota 2 JSON、图标、ID `dota2`，共用 `profiles/.dota2-deleted` 空文件标记。标记在删除配置前写入。两版的降音量键均为 `lowerSpeakerVolumeWhileListening`、布尔、默认关；0.1.14 限于录音，0.2 增加琴音倾听。 |
| 冷启动、常驻内存、包体 | 规模和进程行为会变化 | **必须测**。同机、同构建类型、相同输入法状态分开记录。0.1.13 发布的 x64 NSIS 安装包为 14,784,612 字节。实测与缺口见验证报告。 |
| 安全软件 | VB-CABLE、按进程录音、模拟输入和无 Authenticode 签名会影响评估 | **必须测**。对 Defender、360、火绒分别记录病毒库、安装包哈希、静态扫描和独立机安装/运行。将静态扫描与安装/实际行为分开。未测的不能填“通过”。 |

有效的 0.1.x 旧配置在合并默认值前识别。选择只用语音输入法不会为旧用户新设按键、启用 TTS 等。新用户仍按现行两条引导开始。配置增加的状态字段由旧版忽略。

## 放量提案（数字待确认）

| 阶段 | 方式 | 放行前核对 |
|---|---|---|
| 自愿体验 | 社群招募约 30 人，可手动安装经过签名验证的候选包，先保留备份。不更新旧 latest。 | 升级/降级报告、发行包校验和、三个安全软件结果，以及社群知情参与。 |
| 10% | 专用清单 `rolloutPercent: 10`，观察至少 7 天。 | 真实样本中语音输入、旧热键和待触发提醒工作正常。 |
| 50% | 专用清单 `rolloutPercent: 50`，建议再观察 7 天。 | 上一阶段无语音输入受阻、丢配置、持续误报或异常回退信号。 |
| 100% | 专用清单 `rolloutPercent: 100`。旧 0.1.13 固定地址仍停在 0.1.x。 | 对照报告和反馈，由玩家确认。0.1.x 维护分支至少保留到全量后一个月。 |

建议任何“升级后语音输入用不了”、配置被重置或者安装包被隔离的报告都先停量再复现。另一条候选停量线为连续 2 天的旧版安装包下载显著高于正常基线，增量达到同档人群 0.2 下载量的 5%。这是聚合下载量近似信号，不能当成实际回退人数。下载量来源口径不够时仅参考 Issue 和自愿反馈，不新增遥测、不记录桶号。

专用清单用 `Cache-Control: no-store, no-cache, must-revalidate` 响应。停量时把它换成 0.1.x 或 `rolloutPercent: 0`，用无缓存 GET 确认线上实际清单已生效，并确认两条固定更新地址仍提供 0.1.x。已经显示的更新提示可能仍在，0.1.14 点击安装和验签下载完后都会重新检查。已安装的用户可以手动回退。旧通道发布脚本会拒绝版本号倒退，所以一开始就保留独立清单。
