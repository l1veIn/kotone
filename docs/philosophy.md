# Kotone 的软件哲学（设计和审查的标准）

这份文档有两个用处：

- **做新东西前自查**：加功能、定边界、写 ADR 之前，按这里的问题过一遍；
- **审查整个项目**：Agent 照着这里一条一条查，找出违反的地方（做法见最后一节“怎么审查”）。

它不替代具体规则：开发约定见 [development.md](development.md)，用词见 [glossary.md](glossary.md)，本体和插件的划分见 [ADR 038](adr/038-kotone-and-apps.md)，每个决定的来龙去脉见 [ADR](adr/README.md)。这里讲的是这些规则背后的“为什么”，以及怎么用事实核对。

**和 ADR 冲突时**：ADR 里具体的决定照样有效，但如果某个 ADR 的理由违反了这里的原则（例如理由只是一种感觉、没法核对），这本身就是一条审查发现。

每条原则的写法：**说法** → 为什么 → **怎么查**（尽量是能跑的命令或能数的事实） → **坏味道**（违反时通常长什么样） → 项目里的例子。

## 一、给谁做

### 1. 玩家只要一个 Key 和一个呼叫键

**说法**：玩家装好 Kotone、填一个 Key、记住一个呼叫键，就能用上大部分本事。其余的都有合理的默认值。

- 为什么：Kotone 的玩家在打游戏，没空配置；每多一个必填项，就少一批玩家（ADR 029）。
- **怎么查**：数一下新功能要玩家先设好几样东西才能用；看默认值是不是大多数人想要的；看第一次用到时，她能不能自己带玩家设好（例如游戏语音没装 VB-CABLE 时，她用 `voice_chat.install` 帮着装）。
- **坏味道**：功能默认关、但关着没有任何风险理由；要玩家去设置里找一个开关才能用；报错只说“未配置”，不说怎么办。

### 2. 复杂度留在里面，选能删掉规则的设计

**说法**：同样能做到的几种设计，选让规则变少的那种。玩家对复杂度很敏感。

- 为什么：每条规则都要有人记住、有人测试、有人解释给玩家。能被一个机制代替的规则，就不该存在（例如用 `speak` 工具代替一堆“什么时候该说话”的规则）。
- **怎么查**：看有没有“先看 A，A 不行再看 B”的判断链；看设置项是不是只为一个边角情况服务；看两个开关是不是总要一起改。
- **坏味道**：两个设置管同一件事的两半（每个游戏的“允许程序按键”和“让她操作”，判断时先看前者再看后者，`crates/kotone-core/src/profile.rs`）；同一件事在本体和插件各有一个开关。
- 例子：插件的开关就是原来的功能开关（游戏语音插件开着 = 转发开着），没有再加一层。

### 3. 有风险就提示，不替玩家拦

**说法**：可能违反游戏协议、可能被封号的功能，照样做出来，但要有开关、合理的默认值、写明风险和出处，由玩家决定。

- 为什么：玩家是成年人，比我们更清楚自己愿意冒什么险；拦下来只会让他们去用更不透明的第三方工具。
- **红线（永远不做）**：读游戏内存、往游戏里注入、绕过反作弊。
- **怎么查**：每个有风险的功能都有开关和风险提示，提示里有可点的出处（例如 LeagueAkari #523）；默认值有理由（读本地客户端数据默认开，自动操作客户端默认关）；代码里搜 `ReadProcessMemory`、`WriteProcessMemory`、`CreateRemoteThread`、`SetWindowsHookEx(WH_GETMESSAGE)` 之类，一个都不该出现在游戏进程上。
- **坏味道**：风险功能没有提示；提示里没有出处；把风险功能藏起来不做。

### 4. 玩家的输入是实时的，不替玩家重按

**说法**：Kotone 吞掉的玩家按键就丢掉，不事后替玩家再按一遍（ADR 032）。

- 为什么：游戏状态是实时的，晚了的按键可能比没按更糟。
- **怎么查**：搜代码里有没有把按键存起来、之后再发出去的地方。
- **坏味道**：输入队列、“补发”、“重试按键”。

### 5. 说玩家的话

**说法**：界面上的字照 [glossary.md](glossary.md) 的“界面用语 v2”写，界面文字放在 messages（插件放在自己的 `messages/`）；指她用“她”，不写死角色名。

- 为什么：玩家看不懂“ASR”“OCR”“注入”；角色名可以换。
- **怎么查**：`terminology.spec` 通过；搜 `.svelte` 和 `.ts` 里直接写的中文（应该很少）；搜文案里写死的“琴音”。
- **坏味道**：同一个东西两个叫法；和外部概念撞名（Kotone 的“插件”和 Chrome 的“插件”，后者改叫“扩展”）。

## 二、她（Agent）

### 6. Agent 优先：人能做的，Agent 都能做

**说法**：Kotone 的每一项能力，她能用，外部 Agent 经工具服务、MCP、命令行也能用（ADR 014）。

- 为什么：Kotone 是游戏场景的 Agent 运行框架；能力只有界面能用，就等于锁死在一个入口里。
- **怎么查**：对每一个界面上的功能，找对应的工具；对每一个工具，看在不在 `system.capabilities` 里（工具服务）。
- **坏味道**：只有界面命令、没有工具的功能；只有她能用、工具服务里没有的工具（例如 `browser.*` 目前不在工具服务里）。

### 7. 照成熟项目做，不自己发明

**说法**：Agent 的做法照 Goose、OpenClaw、Hermes Agent、Codex、Claude Code、DeepSeek 的做法；协议照 MCP（含 MCP Apps）；游戏工具照 LeagueAkari、aramhex 这类已经被玩家验证过的项目。

- 为什么：这些项目已经替我们踩过坑；自己发明的东西没有人帮着测。
- **怎么查**：设计文档或 ADR 里写了照的是谁、给了链接；抄代码的地方许可证合规（MIT 可以抄，写进 `THIRD_PARTY_NOTICES.md`；GPL 的不抄；数据集看许可，例如 CC BY-NC 要署名、不商用）。
- **坏味道**：新机制没有任何参照；参照了但没写出处；抄了 GPL 代码。

### 8. 主会话要快，后台要全

**说法**：和玩家说话的主会话只拿马上出结果的一小套工具；慢的、要好几步的交给后台（ADR 029、030）。一段对话里工具清单不变，前缀缓存才命中（ADR 024）。

- **怎么查**：主会话的工具都能在一两秒内返回；工具清单在对话开始时算好，之后不按“现在在玩什么”增减。
- **坏味道**：主会话里出现要等十几秒的工具；对话中途换工具清单。

### 9. 别人写的东西是数据，不是指令

**说法**：网页、战绩、游戏聊天、歌名、别人的文件都是不可信内容；读过它们之后，执行命令、改文件前先经主会话问玩家（ADR 030）。

- **怎么查**：返回外部内容的工具都标了 `untrusted`；读过外部内容的对话有标记，危险操作会先问。
- **坏味道**：工具返回网页原文却没有标不可信；外部内容直接拼进提示词。

### 10. 文字给她，数据给页面

**说法**：工具结果照 MCP 分三份：给她的很短的文字（`content`）、给页面的数据（`structuredContent`）、用哪个页面显示（`ui`）。只有文字进她的上下文。

- **怎么查**：结果里的大块数据（10 个人的战绩、整张榜）只在 `structuredContent` 里；`content` 是她能直接说出口的几句话。
- **坏味道**：把整份 JSON 塞给模型；页面要的数据只能从给她的文字里再解析。

## 三、领域和边界

这一组原则是 2026-11-24 那场“浏览器和 computer use 该放哪”的讨论之后总结的（见 ADR 038“怎么定的”）。目标：从一开始就把边界划得有据，划错了也挪得动。

### 11. 先分单向门和双向门

**说法**：做决定前先问：走错了能不能回头、回头要动什么。只为回不了头的决定花大力气讨论。

- **单向门**（难回头，要慎重）：对外的接口（工具名、工具服务和 MCP 的协议）、配置文件的格式（旧版本会读到）、给插件开的权力（以后“每个插件一个进程”时收不回来）、发到外面的数据（隐私）。
- **双向门**（随时能改，不用怕）：代码放在哪个 crate、哪个目录；开关显示在界面上哪里；内部函数怎么拆。
- **怎么查**：每个 ADR 有没有写“这个决定有多深远：以后要改的话要动什么”。
- **坏味道**：为双向门争论很久；单向门没讨论就定了（例如随手改了工具名，玩家设的权限跟着失效）。

### 12. 本体还是插件：四个问题

**说法**：加一样新本事，先回答四个问题，答案写进 ADR：

1. **谁用它**：她、玩家、还是别的插件？有几个用户？
2. **它要动本体的什么状态**：窗口、全进程只有一份的钩子（Esc、呼叫键）、停下她、免问？
3. **关掉它会连带谁**？
4. **放错了以后挪，要动什么**？是单向门还是双向门？

**判断**：有两个以上的用户，或者要动本体的状态 → 放本体；否则 → 做成插件（ADR 038 D2：本体 = 她、感官和表达〔耳、眼、嘴、手〕、自动化、宿主）。

- 为什么：四个答案都是能拿代码核对的事实，不靠“它像什么”“玩家会不会单独打开它”这类感觉。原来写进 ADR 038 的“玩家不会单独打开浏览器”就是一句感觉，一问就晃。
- **怎么查**：每个插件、每个本体模块都能对上这四个答案；答案和代码一致（谁 `use` 了它、它调了本体的什么）。

### 13. 依赖只朝稳定的方向

**说法**：被很多地方依赖的东西放在稳定的一层；依赖只能从易变的指向稳定的（Robert Martin 的稳定依赖原则；Parnas 的信息隐藏：每个模块藏住一个可能会变的决定）。

- 在 Kotone：`kotone-core` 不反向依赖平台、语音识别、网络实现（[development.md](development.md)）；插件依赖 `kotone-plugin-api`、`kotone-core`、自己的第三方库，可以用 `kotone-platform-windows` 里没有状态的系统调用和 MCP 客户端 `kotone-mcp`，不碰 Tauri、桌面端、她（`kotone-agent`、`kotone-ai`）；插件之间不直接调用。
- **怎么查**：看每个 crate 的 `Cargo.toml`；`cargo tree -p <crate> -i <被依赖的 crate>` 看谁依赖了谁；搜插件源码里有没有用到全进程只有一份的东西（低级钩子、热键）。
- **坏味道**：本体的“眼睛”依赖某个插件；两个插件互相 `use`；一个模块被五处 `use`，却放在最容易变的地方。

### 14. 第二个用户出现再抽象

**说法**：先把代码写在用到它的地方；第二个地方也要用时，再抽成共用的能力（本体给插件的能力、共用的模块）。

- 为什么：只有一个用户的抽象，多半抽错了形状。Kotone 先只做英雄联盟一个插件，再定插件契约，契约后来就没大改。
- **怎么查**：数每个公开接口、每个 `Host` 方法有几个调用方。
- **坏味道**：只有一个调用方的接口和“以后可能用到”的参数；反过来，同一段逻辑复制了三份。

### 15. 一种东西只有一种登记方式

**说法**：同一类东西用同一种方式登记，例如工具都用 `ToolSpec` 登记（名字、说明、参数、副作用、只给后台、不可信……），本体的和插件的一样。

- 为什么：登记方式统一，挪位置就只是挪文件，放错了也不怕（原则 11 的双向门才真的是双向门）。
- **怎么查**：搜写死的工具名单（例如 `catalog.rs` 里的 `SERVICE_MAIN`、`SUBAGENT_EXCLUDED`，提示词里点名的工具，宿主里按名字 `match` 的分支），每一张名单都是一个“没走统一登记”的地方。（2026-11-25：原来的 `MAIN_TOOLS` 已经改成每个工具登记时自己标 `ToolEntry::main`，只剩工具服务那几个在 `SERVICE_MAIN`，MCP 方案第 1.5 期。）
- **坏味道**：加一个工具要改五个文件；某个工具的超时、步数写死在别处的名单里。

### 16. 边界写成测试

**说法**：边界规则不只写在文档里，还要写成测试，违反了就报错。

- 为什么：只写在文档里的规则会被悄悄违反。游戏语音插件用了系统适配层，和文档里写的规则冲突，直到讨论时才被发现。
- **怎么查**：每条边界规则（插件不碰 Tauri、插件之间不调用、工具名不重复、文案和清单一致……）都能找到对应的测试；文档里的规则和测试一致。
- **坏味道**：文档写“不许”，代码里却有，测试也不管。

### 17. 新概念先进术语表

**说法**：新的领域概念先在 [glossary.md](glossary.md) 定名，再写代码和界面。

- **怎么查**：代码里的模块名、界面上的叫法、文档里的叫法是同一个词；没有两个概念共用一个词。
- **坏味道**：同一个东西在代码、界面、文档里三个名字；Kotone 的词和外部的词撞名。

## 四、代码

### 18. 一个文件只管一件事

**说法**：新功能放新文件；按职责拆，不按行数拆（[development.md](development.md)）。

- **坏味道**：一个文件里既有界面命令、又有业务逻辑、又有存储；为了凑行数把一件事拆到三个文件。

### 19. 旧版本也要能读新配置

**说法**：已有字段只写旧版本认识的值；新能力用新字段；搬家时读旧的、写新的，已有的新字段不被旧字段覆盖，并且有测试（[development.md](development.md)“配置兼容”）。

- 为什么：玩家可能装回旧版；旧版读到不认识的值，会把整份配置当成坏的。配置格式是单向门。
- **怎么查**：每次配置搬家（`lol.enabled`、`voiceChat`、`music` 搬进插件）都有“旧配置读进来”的测试；没有给已有字段加新的取值。

### 20. 不卡住，能取消

**说法**：锁里不做网络、音频设备、模型加载这类可能很慢的事；异步结果交回之前，再核对一次是不是还是同一轮（[development.md](development.md)）。

- **坏味道**：持锁等网络；结果回来时不看代际，旧结果盖掉新的。

### 21. 出错要说人话、说下一步

**说法**：给玩家和给她的错误信息都说清楚“怎么了、下一步怎么办”，例如“还没有安装 VB-CABLE（voice_chat.install）”。

- **坏味道**：只有英文错误码；“操作失败”；把内部异常原样抛给玩家。

## 五、验证

### 22. 真机才算数

**说法**：编译通过、单元测试通过，都不能代替真机验收。每一步都有能重复跑的真机脚本（`scripts/manual-e2e/`），写明前置条件、结果，以及没测到的地方。

- **怎么查**：每个跟游戏、声音、窗口、模型打交道的功能，都有对应的真机脚本，或者写明了为什么没有；实施记录里有“还没测”这一节。

### 23. 测试不打扰玩家

**说法**：测试用隔离的 `KOTONE_HOME`，不碰玩家的配置；真模型测试禁掉会按键的工具；只有测试窗口在前台时才发按键；玩家在打游戏时，构建用低优先级、少开线程。

- **坏味道**：测试往玩家的前台窗口打字；测试读写 `~/.kotone`；比赛中跑满 CPU 的构建。

### 24. 如实报告

**说法**：没测的就写没测；不稳定的测试写明是哪一个；失败照实贴输出，不说“基本通过”。

## 六、文档和决定

### 25. 决定写进 ADR，理由要能核对

**说法**：重要的取舍写 ADR，写清楚：怎么定的（附玩家原话）、照的是谁、有多深远（原则 11）、哪些事实会让我们改主意。理由要能拿代码或数据核对，不写只是感觉的理由。

- **坏味道**：ADR 只有结论没有理由；理由是“应该”“更好”“玩家不会……”这种没法核对的话；改了决定却没在 ADR 里留痕。

### 26. 文档和代码不一致时，同一次改掉

**说法**：发现文档和代码冲突，在同一次变更里修正，不另开一份清单（[docs/README.md](README.md)“维护规则”）。

## 怎么审查（给 Agent）

**分工**：一个 Agent 一块，互不重叠。建议这样分：

1. 本体和插件的边界（原则 11–16）：`crates/`、`plugins/`、`apps/desktop/src-tauri/src/plugins.rs`；
2. 她的工具和提示词（原则 6–10、15）：`crates/kotone-agent`、`crates/kotone-tools`、各插件的工具；
3. 玩家看到的（原则 1–5）：`apps/desktop/src`、`plugins/*/ui`、`messages/`、默认设置；
4. 代码和配置（原则 18–21）：配置的读写和迁移、锁和取消、错误信息；
5. 验证（原则 22–24）：测试、`scripts/manual-e2e/`、实施记录里的“还没测”；
6. 文档和决定（原则 25–26、17）：`docs/`、ADR、术语表。

**先读再查**：先读 [ADR 038](adr/038-kotone-and-apps.md) 和相关 ADR 的“怎么定的”。ADR 里已经定的事，除非拿出新的事实，不要重新争论；有新事实就写明是什么事实。

**每条发现写成这样**：

| 项 | 写什么 |
| --- | --- |
| 原则 | 编号和名字，例如“15 一种东西只有一种登记方式” |
| 位置 | `文件:行` |
| 事实 | 能核对的证据：代码片段、命令和输出、数出来的数 |
| 为什么违反 | 一两句 |
| 单向门还是双向门 | 改它要动什么 |
| 严重程度 | **伤玩家**（玩家会遇到错误、风险、困惑）/ **以后难改**（单向门、扩散中的坏味道）/ **只是不整齐** |
| 建议 | 怎么改；有成熟项目的做法就给出处 |

**不要做的**：审查时不改代码；不写“我觉得”；同一件事只报一次（报在最根本的那条原则下）；不为凑数报“只是不整齐”的小事，除非它在扩散。

**最后交**：按严重程度排序的清单；每条原则一句“整体情况”（例如“原则 13：大体遵守，有 2 处例外”）；以及你认为这份标准本身该改的地方。
